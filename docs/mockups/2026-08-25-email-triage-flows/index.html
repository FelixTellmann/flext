What actually runs on your mail, and what a dwell clock would change

Six phases shipped. Every decision the system makes today is a pure function of message headers and the sender graph — no model, no read-state, no clock beyond message age. This is the whole machine, drawn, plus an honest read on the dwell-and-read-state proposal.

01

One sync run, start to finish

A cron POST to /api/mail-sync runs runSyncForAllMailboxes. Each mailbox is isolated — a dead connection fails that mailbox and leaves the other five untouched. Inside a mailbox the five stages run in a fixed order, and the order is load-bearing in two places.

Scoping

Stage 4 only ever looks at messages that have never been classified — no Action row of any kind. New mail is the only input a scheduled run can have seen change, so re-deciding the rest buys nothing. This is the single biggest structural obstacle to a dwell clock: a message classified once on arrival is never reconsidered, no matter how long it sits.

02

The decision ladder

Everything narrows to one pure function, decide(). It takes headers, the sender graph, thread state and the policy table, and returns exactly one outcome. It performs no IO and knows nothing about a mail server, which is why the whole thing is testable from fixtures.

Resolution runs top to bottom and stops at the first rung that answers. The last rung is the safety spine.

03

Guards: three that stop everything, three that only stop destruction

An earlier draft made every guard absolute. That was fatally wrong: two of the guards are "I have replied in this thread" and "I have written to this sender" — and client correspondence is by definition mail you reply to. Absolute guards would have made automatic filing unreachable and quietly deleted the record-keeping half of the product.

So guards are scoped per action class. The three that protect against destruction never block organisation.

Override rule

An address-scoped policy you created by hand outranks all three scoped guards — but never the absolute ones. Otherwise a policy you deliberately made would sit in the dashboard as silent dead code. Where a scoped guard does suppress a policy, the Sender Policy screen renders suppressed by guard: <name> on that row, so an inert policy is never indistinguishable from an active one.

04

Autonomy is per policy, and it can revoke itself

No policy is ever born trusted. Every one enters at shadow, where the decision is computed and journaled and the mailbox is untouched. Promotion is per policy, after you read its shadow record — so "LinkedIn notifications: auto" and "Acme filing: still proposing" coexist naturally.

The interesting edge is the one going backwards.

05

Where the AI is: nowhere

You asked how AI really scans your mail for what's valuable. The honest answer is that it does not, and that this was deliberate twice over — then a third time by accident.

By design, no model is ever in the execution path. Classification is a pure function over headers and stored sender policy. The unit of classification is the sender, not the message: a few hundred senders account for the overwhelming majority of six mailboxes' traffic, so AI's intended job was to help build the sender-policy table once, after which rules execute it indefinitely, deterministically, at zero marginal cost — and reproducibly after the fact.

By design, the AI boundary cannot mutate a mailbox. Email subjects are attacker-controlled text, and indirect prompt injection against AI mail assistants is a demonstrated, CVE-bearing attack class. So the planned MCP server has exactly one write — propose_policy, which inserts a row awaiting your approval. A fully hijacked session can create a bad proposal. That is the entire blast radius.

And by accident: it was never built. Phase 7 is the MCP surface, and it has not shipped. There is no MCP server in the repo, no Proposal table in the schema, no proposals inbox. Phase 8, the irreversible purge sweep, is likewise unbuilt — purge is refused at four separate layers.

06

Why your inbox still has unread mail in it

Nothing above is broken. The system is doing exactly what it was designed to do — and what it was designed to do does not include the thing you now want. Five concrete gaps sit between here and a dwell clock.

  1. 01Read-state never reaches the classifier. is_seen exists on every message row, but decide() does not take it as an input. It is read in exactly two places, both cosmetic: unread counts on the Senders screen, and a reason string on Needs Action.
  2. 02A message is classified once, on arrival, and never revisited. The scheduled pass filters to rows with no Action row of any kind. Dwell is by definition a decision that changes as time passes — so it needs a second pass with the opposite scoping.
  3. 03Age is measured from the send date, not from when it landed in front of you. age_days comes off internalDate. There is no "how long has this sat in my inbox" and no "how long since I last touched it".
  4. 04The system cannot mark anything read. The provider exposes exactly three mutating methods — moveMessages, setLabels, createFolder. Writing \Seen is a fourth mutating verb that does not exist, and it needs its own inverse for undo. This is why quarantined first contacts still sit unread in Quarantine/.
  5. 05There is no destination for the unclassified middle. Mail with no policy, no client, no bulk headers and a known sender falls to rung 7. Sweeping it somewhere means naming a folder the system currently has no concept of.
The real objection

Every one of the five is buildable. The one that deserves an argument is different: your proposal inverts the invariant the whole system rests on. Today, "no rule matched" means "leave it alone" — silence is safe. Under a dwell clock, "no rule matched, and two days passed" means "move it". The default flips from inaction to action, and every safety property in sections 02–04 was designed around the old default.

07

The change, and the one substitution that makes it safe

Your rules were: read mail stays 7 days; unread mail gets filed and marked read after 2; flags freeze anything. Your own stated risk was the right one — "if I don't check email for more than 2 days, I'd miss something" — and you then answered it yourself in the next paragraph, without quite noticing.

Wall-clock dwell is the wrong clock

"Unread for 2 days" conflates two completely different states. A message you saw in the list and scrolled past has been offered and declined — that is real evidence. A message that arrived while you were on a plane has no evidence attached to it at all. Wall-clock time cannot tell them apart, which is exactly why the away-for-three-days case is dangerous.

So replace the clock with a counter: how many times have you opened your inbox while this message sat unread in it? If a triage session is detectable, then "declined in 3 sessions" is a far stronger signal than "unread for 2 days", and it degrades correctly — go away for a week, no sessions happen, nothing ages out, nothing is missed. The safety property you were worried about becomes structural instead of a gamble.

Can a triage session actually be detected?

Yes, and your instinct about the shape of the evidence was right — "I've read 2 emails and ignored 10 would be a good sign that I've checked my inbox." IMAP gives no login timestamp, but the sync already witnesses every flag transition through CONDSTORE. Any of these, observed in one sync window, is evidence that a human was in the mailbox: an unseen→seen transition, a flag being set or cleared, a message moved by hand, or a new message in the Sent folder.

One caveat, and it is a real one. openedAt is stamped only on transitions the sync witnesses. Mail that was already read when it was backfilled carries no timestamp at all, and on the largest mailbox that is 4,715 of 4,719 messages. Historically the system is close to blind here. Going forward it is not — every transition from now on is observable — but that means a session detector has no history to calibrate against and has to accrue its own from the day it ships.

Quarantine should mark read on the way out

Today a first contact is moved to Quarantine/ and left unread, so the unread badge follows it into the folder and you carry the count around without ever seeing the mail. Marking it \Seen in the same batch as the move is the cheapest possible version of this change and the least contentious: the message is being hidden from the inbox either way, and its unread state is a claim about your inbox that stops being true the moment it leaves. It is also the natural first customer for the new setFlags verb — a single, narrow, easily-undone use to prove the mutation and its inverse before the dwell sweeps depend on it.

Settled is the rule that actually empties your inbox, and it is also the safest of the three — a message you have read and left alone for a week is the clearest possible statement that it needs no further inbox presence. It is worth noticing that this one needs no session detector at all and could ship on its own, first, as a much smaller change than the rest.

The flag trap — decided, and accepted

Flagging freezes a message permanently, so once sweeps exist the flagged set only ever grows and reconstitutes the same clutter with stars on it. Put with two alternatives — a 30-day expiry, or release via the thread done state — and deliberately accepted as-is: no new habit, no schema change, and flags here are applied sparingly enough to grow slowly. Recorded as a decision rather than an oversight, with a falsifiable trigger: if the held count passes 200, or grows by 50 in a month, it failed in the predicted way and expiry gets built.

What has to change in the rescue loop

Rescue detection responds to a mistake by suspending the policy that caused it. A dwell sweep has no policy — so an over-eager sweep has nothing to suspend and would keep firing forever. The dwell rules need their own feedback: a rescue on a swept message should lengthen that mailbox's dwell threshold, or pause sweeping outright, rather than being silently discarded because there was no policy id to blame.

Five branches, grilled and closed

The design above was interrogated decision by decision on 25 August. Three of the holes were mine.

  1. 01The sweep sits second-to-last in the ladder. As first written it "honoured the ladder's verdict" — which for nearly every candidate is keep_inbox from the fallback, so it would have archived nothing, ever. It now fires only where steps 1–6 had no opinion. Side effect worth having: an explicit keep_inbox policy becomes the permanent pin for a sender.
  2. 02Sessions are global, not per mailbox. Per-mailbox counting assumed you visit mailboxes one at a time. You read one unified list, so five of six mailboxes would have recorded no session and never swept — and those are exactly the ones filling with noise. Safe direction, wrong outcome.
  3. 03Needs Action mail sweeps at six declines, into Followup/. buildWhere in the Needs Action query has no folder predicate, so a swept message stays on that screen. It leaves the inbox and the unread count, not the surface built to catch it.
  4. 04The 7-day sweep ignores the replied-in-thread guard. That guard stops sender rules archiving live client mail. A thread you answered and haven't touched in a week is the textbook settled thread — and on Gmail archive is a label removal that restores in one click.
  5. 05Flags stay permanent. Decided, not defaulted — see the note above.
One idea rejected, and what it improved anyway

Stamping system-written read timestamps with a fixed millisecond suffix, so system stamps stay recognisable, was proposed and turned down: it writes a false fact and then marks it false, and the marker is destroyed by any fsp change on restore, by driver truncation, or by the re-key path — each of which fails open, reading as a genuine human open. One real read in a thousand also collides with the sentinel and is silently discarded, which for a safety net is the worst available direction. But the worry underneath was right, and it produced a rule the design was missing: the session detector must count seen transitions through the stored-state guard, never raw CONDSTORE reports — otherwise the sweeps manufacture their own triage sessions and accelerate their own clock.
