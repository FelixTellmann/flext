flext — MAIL SYNC SCHEDULED TASKS (Coolify)
Written 2026-08-17. Copy the two blocks below into Coolify.

Where: Coolify -> project flext.dev -> application flext.dev -> Configuration -> Scheduled Tasks -> + Add.
Each task needs four fields: Name, Command, Frequency, Container name.

LEAVE "Container name" EMPTY. The running container's name carries a per-deployment suffix that changes every time you redeploy (…-145534209802 one day, …-090433712376 the next), so anything hardcoded there breaks silently at the next deploy. Coolify resolves the container itself for a single-container application.

The commands use only double quotes inside single quotes — no backticks and no ${...} — so they survive whatever quoting Coolify wraps around them.


=============================================================================
IMPORTANT: DO NOT USE curl
=============================================================================

Coolify runs scheduled tasks INSIDE the application container, and this image has no curl. The Dockerfile deliberately omits it (see its HEALTHCHECK comment: adding curl would reintroduce the apt layer the Dockerfile exists to remove). A curl command here fails with "curl: not found" and the task looks broken for no reason.

VERIFIED IN THE CONTAINER on 2026-08-17 via Coolify -> Terminal, rather than assumed from the Dockerfile:

    # which curl bun
    /usr/local/bin/bun
    curl_exit=127            <- 127 is "command not found"

    secret_len=48            <- SCRIPT_SECRET is present in the container
    http 401 Unauthorized    <- the bun command below works; 401 because the token was wrong on purpose

The container does have bun, so the commands below use bun's fetch — the same approach the container healthcheck uses. They call 127.0.0.1:3000 directly, which skips DNS, TLS and the reverse proxy entirely. SCRIPT_SECRET is read from the container environment, so the secret never appears in the task definition.

=============================================================================
RUNNING A BACKFILL BY HAND
=============================================================================

Run backfill from a terminal, not the browser: the /admin/mail button holds one HTTP request open for the whole walk, and a ten-minute request shows "Failed to fetch" in the browser even though the server completes it normally (this happened on 2026-08-17 — the run succeeded with 10027 messages while the UI reported failure).

From your laptop, one mailbox at a time. Get the id from /admin/mail or from the Mailbox table:

curl -fsS --max-time 3600 -X POST -H "Authorization: Bearer $SCRIPT_SECRET" "https://flext.dev/api/mail-sync?mode=backfill"

Note this endpoint backfills EVERY enabled mailbox in sequence; per-mailbox backfill is only exposed through /admin/mail. --max-time 3600 matters, as curl's default timeout will cut a long walk.


=============================================================================
REPAIR AND RECLASSIFY — ONE-OFF MODES, NEVER SCHEDULE THESE
=============================================================================

Same rule as backfill above, and just as absolute: mode=repair and mode=reclassify
are one-off operator actions. Do NOT add either one to Coolify's scheduled tasks.
repair fixes up existing rows once; reclassify re-derives classification once after
you widen identity_addresses. Neither belongs on a cron line, ever.

These two exist because of the Phase 2 data-quality findings written up 2026-08-18:
senderId linkage was incomplete and to_me/dkimAligned were wrong for mailboxes whose
identity_addresses didn't cover every address that mailbox actually receives at.

THE ORDER MATTERS. Do these in this exact sequence:

  a. Apply the pending database migration first.
     Task 1 of the Phase 2 dashboard work generated
     server/db/migrations/0002_absurd_cyclops.sql (two CREATE INDEX statements,
     on Message.fromAddress and Message.internalDate) and it has NOT been applied
     yet. Run:

         bun run db:migrate

     The dashboard works without this — it's just slower on the Senders and Needs
     Action pages until the indexes exist.

  b. Set identity_addresses on EVERY mailbox at /admin/mail, using the new
     observed-address picker. Do this for all four mailboxes, not just the one
     you think is wrong — repair and reclassify below run once for whatever
     identity_addresses holds at the time, so an incomplete pass here means
     redoing the whole sequence.

  c. Run repair once. Database-only, touches no mailbox, fast.

  d. Run reclassify. Re-fetches headers from every mailbox over IMAP, slow —
     see the duration note below. Run it from a terminal, not the browser,
     for the same "Failed to fetch" reason as the backfill note above: a long
     request against /admin/mail's button dies in the browser tab while the
     server keeps running it to completion.

  e. Re-check the numbers (see below for what "correct" looks like).

-----------------------------------------------------------------------------
TIMEOUT TRAP: YOUR CLIENT GIVES UP LONG BEFORE THE RUN FINISHES
-----------------------------------------------------------------------------

Hit on 2026-08-18 during the first real reclassify. The client gave up with a
timeout while the server carried on working to completion. The run looked like
a hard failure and there was nothing in the output to say otherwise.

Do NOT re-run when this happens. A second reclassify against the same mailboxes
would run concurrently with the first. Instead, check whether it is still going:

    SELECT mailboxId, status, startedAt, finishedAt, messagesUpdated
    FROM SyncRun WHERE kind = 'reclassify' ORDER BY startedAt DESC;

A row with status='running' and no finishedAt means it is still working. The
reclassify cursors also advance as it goes, so re-reading MailboxCursor a minute
apart shows movement:

    SELECT mailboxId, folder, lastSeenUid, lastSyncAt
    FROM MailboxCursor WHERE kind = 'reclassify';

Always pass an explicit long timeout. With curl that is --max-time 3600, as in
the backfill section above. Anything driving this with fetch needs the same:
bun's default timeout is minutes, and reclassify took 13 minutes across four
mailboxes on 2026-08-18 (82s + 97s + 188s + 406s).

-----------------------------------------------------------------------------
THE TRAP: A REPEAT RECLASSIFY RUN CAN BE A SILENT NO-OP THAT REPORTS SUCCESS
-----------------------------------------------------------------------------

READ THIS BEFORE RUNNING RECLASSIFY A SECOND TIME.

reclassify checkpoints its progress per folder in MailboxCursor, kind='reclassify'.
A folder that finishes leaves its cursor parked at uid_next - 1 — the folder's
highest UID. If you then widen identity_addresses again and run reclassify again
WITHOUT clearing that cursor, reclassify resumes just past that UID, finds nothing
left to examine, and exits having examined zero messages. It still logs a SyncRun
row with status=ok. There is no error, no warning, nothing that looks wrong.
It looks exactly like a healthy run that had nothing left to do — because from the
cursor's point of view, that's true.

Before ANY repeat reclassify run — i.e. every time after the first — clear the
cursor first:

    DELETE FROM MailboxCursor WHERE kind = 'reclassify';

If you skip this and rerun reclassify after changing identity_addresses, the
numbers will not move and you will have no way to tell, from the run's own output,
that it did nothing.

A UIDVALIDITY change has the same shape, from the opposite direction. When the
server hands back a new uid_validity, reclassify.ts drops the resume point to 0
and re-fetches the whole folder, but the stored-classification lookup it joins
against filters on the NEW uid_validity — and every Message row still carries the
old one. Nothing matches, so the pass examines the folder end to end and writes
zero rows. Same symptom: SyncRun status=ok, numbers unmoved, no warning. If a
reclassify walks a large folder and reports no changes, check whether that
folder's uid_validity moved before assuming the identity list was already right.

-----------------------------------------------------------------------------
DURATION
-----------------------------------------------------------------------------

reclassify re-fetches headers for every stored message across every enabled
mailbox — there's no shortcut, it's a full re-walk. Judge the time from the
recorded backfill figure, since reclassify walks the same UID space at a
comparable per-batch cost: 10,027 messages took 597 seconds for
felix@tellmann.co.za. With ~14,500 messages across four mailboxes, budget on that
order for the full run — run it from a terminal and let it finish, don't judge it
by whether the browser tab is still spinning.

mode=reclassify has NO per-mailbox filter — the route never parses a mailbox_id,
so it processes every enabled mailbox in sequence, same as backfill. If you want a
scoped, single-mailbox run, temporarily disable the other mailboxes at /admin/mail
first, run reclassify, then re-enable them.

Command, same bun -e fetch form as everywhere else in this file — the container
has no curl (see the warning at the top):

    bun -e 'const r = await fetch("http://127.0.0.1:3000/api/mail-sync?mode=repair", {method:"POST",headers:{authorization:"Bearer "+process.env.SCRIPT_SECRET}}); console.log(r.status, await r.text()); process.exit(r.ok?0:1)'

    bun -e 'const r = await fetch("http://127.0.0.1:3000/api/mail-sync?mode=reclassify", {method:"POST",headers:{authorization:"Bearer "+process.env.SCRIPT_SECRET}}); console.log(r.status, await r.text()); process.exit(r.ok?0:1)'

=============================================================================
CHECKING THAT IT IS WORKING
=============================================================================

In Coolify the task's own log shows the HTTP status and the JSON summary per run.

In the database, the authoritative record is SyncRun:

SELECT kind, status, startedAt, messagesNew, messagesVanished, LEFT(IFNULL(errorMessage,'-'),80) FROM SyncRun ORDER BY startedAt DESC LIMIT 10;

Healthy incremental runs show status=ok with small messagesNew. A mailbox that goes wrong also records Mailbox.lastError, and an auth failure or a pinned-SPKI mismatch sets Mailbox.enabled=0 deliberately, so it stops retrying until you look at it:

SELECT label, enabled, LEFT(IFNULL(lastError,'-'),60), lastErrorAt FROM Mailbox;

PHASE 3 — RULES ENGINE AND SHADOW MODE (added 2026-08-19)
=============================================================================

Phase 3 adds a rules engine, per-sender policies, and a shadow pass that
journals what the rules WOULD do without touching any mailbox. This
section is the operator sequence for turning it on. Do the steps in this
exact order — the order is not obvious and getting it wrong loses data.


-----------------------------------------------------------------------------
THE ORDER
-----------------------------------------------------------------------------

  1. Apply migration 0004:

         bun run db:migrate

     This adds Action.source.

  2. Seed the sender policies:

         bun --env-file=.env scripts/seed-sender-policies.ts --apply

     Without --apply this is a dry run and writes nothing. The flag is
     required, not a safety default you can leave off by habit.

  3. Run a shadow pass, per mailbox, via the trigger on /admin/shadow or
     the runShadowPass procedure. It requires an explicit mailbox id —
     there is no "run for everything" trigger.

  4. Read the shadow report at /admin/shadow and decide what has earned
     promotion out of shadow.


-----------------------------------------------------------------------------
THE ORDERING HAZARD: 0004 BEFORE ANY SHADOW PASS, ALWAYS
-----------------------------------------------------------------------------

Migration 0004 adds Action.source as NOT NULL with NO DEFAULT. Action is
empty today and MySQL strict mode is on, so applying 0004 right now is
completely clean.

But if a shadow pass runs FIRST, Action gains rows before the column
exists. The ALTER then either backfills those rows with a meaningless
empty string or fails outright — and source is exactly the field that
makes a promotion decision sound: it is what lets the shadow report tell
"this policy would have fired" apart from "a guard suppressed it" apart
from "a suspended policy sat there inert, doing nothing". Losing it on
rows that already exist defeats the reason this column exists.

0004 before any shadow pass. Always.

-----------------------------------------------------------------------------
WHAT A SHADOW PASS DOES AND DOES NOT DO
-----------------------------------------------------------------------------

A shadow pass reads stored metadata, runs it through the rules engine, and
journals one decision row per message.

It opens NO mailbox and moves NO mail. Nothing is deleted, flagged,
moved, copied, or appended anywhere. That is exactly what makes it safe to
run repeatedly — a bad rule can be fixed and re-run with no cleanup
required, and it is why the report can be trusted enough to promote a
rule: running it changed nothing real.

-----------------------------------------------------------------------------

As of this write-up the Needs Action queue stands at roughly 7,535 threads

=============================================================================
PHASE 4 — THE FIRST REAL MAILBOX MUTATION (added 2026-08-19)
=============================================================================

Phase 4 adds the executor, undo and the Action Journal. It is the first
code in this project that can move or delete a real message.

Nothing in it has ever touched a real mailbox. Every mutating path was
verified by typecheck, by unit tests over a fake provider, and by reading.
Those tests assert which IMAP commands get issued; they cannot prove a real
server answers them the way the code expects. So the sequence below is not a
smoke test to get through — it IS the acceptance test for the whole phase,
and it is the only thing that will tell you whether the executor and undo
actually work.

Do it once, deliberately, on one message you would not mind losing.


-----------------------------------------------------------------------------
THE ORDER — EACH STEP DEPENDS ON THE ONE BEFORE IT
-----------------------------------------------------------------------------

  1. Apply migration 0005:

         bun run db:migrate

     server/db/migrations/0005_bumpy_lily_hollister.sql adds Action.mailboxId
     (nullable) plus an index on (mailboxId, status). It has NOT been applied
     yet — as of this write-up

         SELECT COUNT(mailboxId) FROM Action;

     still fails with ER_BAD_FIELD_ERROR. Nothing below works until it does.

  2. Re-run a shadow pass, per mailbox, from /admin/shadow.

     REQUIRED, not optional. See the next section for why: without a fresh
     pass, Phase 4 is inert and every approve button does nothing.

  3. Review the shadow report at /admin/shadow and pick ONE decision.

  4. Approve exactly one decision. The approval ceremony differs by what the
     decision would do:

       - a destructive decision (trash) makes you TYPE the phrase
         APPROVE TRASH — a checkbox is not enough
       - an organisational decision (archive, keep_inbox) needs only the
         acknowledgement checkbox
       - a file decision cannot be approved at all in this phase; the button
         is disabled and says why. See "what Phase 4 deliberately left out"

     For the first ceremony, an organisational single row is the sane choice.

  5. Apply it. The "Apply approved actions" panel lives on the Needs Action
     and Senders screens (same component, both places). It takes ONE mailbox
     and a batch size — there is deliberately no apply-everything button.

     USE BATCH SIZE 1. The default is 25.

  6. Go and look in the actual mail client. Not the dashboard — the mail
     client. Confirm the message is where the decision said it would go and
     that nothing else moved.

     This is the step the tests cannot do for you, and it is the whole point
     of the ceremony. Do not skip it because the journal says "applied": the
     journal records what the code believes happened.

  7. Undo it from the Action Journal at /admin/journal.

  8. Go and look in the actual mail client AGAIN. Confirm the message is back
     in its original folder and — on Gmail — that its labels came back too.
     See "Reasoned but never measured" below for why the labels are the
     interesting half.

  9. ONLY THEN approve a batch.

Steps 6 and 8 are the acceptance test. Steps 1-5, 7 and 9 are plumbing
around them.


-----------------------------------------------------------------------------
THE BLAST RADIUS OF ONE CLICK — TWO BOUNDS, NOT ONE
-----------------------------------------------------------------------------

Apply and undo are NOT bounded the same way, and reading the apply bound as
the phase's maximum understates undo by a factor of the mailbox count.

APPLY — 200 messages, in ONE mailbox. applyPending takes a single mailbox_id
string and there is no all-mailboxes option anywhere in its input. The batch
size defaults to 25 and is capped at MAX_ACTION_BATCH_SIZE = 200, clamped
client-side and again by the ORPC input schema.

UNDO BY POLICY — 200 messages PER MAILBOX, across every enabled mailbox.
undoByPolicy takes mailbox_id: string | null, and null is what the journal
screen offers by default ("Every enabled mailbox"). The handler loops the
mailboxes and hands the SAME batch size to each, so the batch size bounds
each mailbox separately rather than the sweep: 200 x the number of enabled
mailboxes, which is 800 with the four here. Each row costs up to two
mutations — the move back, then the set_labels restoring what from_state
recorded — so up to 1,600 writes reach real servers from that one click.

Neither figure is one to go near on a first run. Step 5 of the ceremony says
batch size 1 for this reason, and the undo panel lets you name a single
mailbox instead of taking the default.


-----------------------------------------------------------------------------
WHY THE SHADOW PASS MUST BE RE-RUN — PHASE 3'S ROWS CANNOT BE APPROVED
-----------------------------------------------------------------------------

Until commit 9c08118 the shadow runner never recorded action.mailbox_id, so
every one of the roughly 29,000 rows a Phase 3 pass wrote has that column
NULL.

Phase 4 matches on that column everywhere it matters:

    promoteAction              (server/mail/actions/promote.ts)
    loadShadowActionsByPolicy  (server/mail/actions/journal.ts)
    loadPendingActions         (server/mail/actions/journal.ts)
    loadActionForUndo          (server/mail/actions/journal.ts)
    loadUndoableActionsByPolicy(server/mail/actions/journal.ts)

A NULL there matches no mailbox, so those rows are readable and permanently
un-approvable. Approve one and the answer is "that action belongs to mailbox
(none recorded)". The /admin/shadow list labels them, so this is a known
limitation rather than a dead button — but if you skip step 2, EVERY row you
can see is one of them and the whole phase does nothing.

NO BACKFILL OF THE OLD ROWS IS NEEDED. Don't write one. The shadow report
reads only the latest run id, so a fresh pass both mints rows with the column
populated and is what the report shows you. The old rows just sit there.

expungeUids, and the final review found neither had ever had a caller: the
no-MOVE fallback uses private helpers inside imap.ts, not the public
methods. Both were deleted. A public expunge was the only way this contract
could delete mail, and an entry no one calls misstates the blast radius
rather than merely sitting there — Phase 8 adds back whatever its sweep
genuinely needs. createFolder is held to the same standard: it creates, and
it cannot delete, rename, unsubscribe or move anything, and a folder that
already exists is success rather than an error.


-----------------------------------------------------------------------------
§11 ERROR HANDLING — WHAT YOU WILL ACTUALLY MEET
-----------------------------------------------------------------------------

A PARTIAL BATCH FAILURE MARKS ONLY THE UNCONFIRMED UIDS FAILED. COPYUID tells
the executor exactly which UIDs the server confirmed; the rest are marked
failed individually. It does not assume the whole batch went one way. The
executor re-reads state on its next run rather than carrying a belief forward.

A MISSING UIDPLUS HARD-FAILS. It does not fall back. This is deliberate and
it is the single most important refusal in the phase: without UIDPLUS there
is no UID EXPUNGE, only a bare EXPUNGE, and a bare EXPUNGE destroys EVERY
\Deleted-flagged message in the folder — including ones you flagged by hand
in a mail client ten minutes earlier. imapflow's own messageMove emulates a
move with COPY + messageDelete when the server lacks MOVE, and that is the
path that degrades to a bare EXPUNGE, which is why imap.ts branches on MOVE
itself instead of delegating (see the comment at imap.ts:322).

A CRASH MID-BATCH LEAVES PENDING ROWS. The next run reconciles them; the
pre-state was journalled before the mutation was issued, so nothing is lost.

A PENDING ROW DOES NOT PROVE THE MUTATION DID NOT HAPPEN. This is the one
that will mislead you. The pre-state is written before the mutation and the
outcome after it, so markFailed can itself fail on a mutation that actually
succeeded. Only comparing real server state against the row's from_state and
to_state settles what happened. The apply panel says this on screen for the
same reason.


-----------------------------------------------------------------------------
REASONED BUT NEVER MEASURED — WATCH THESE ON THE FIRST RUN
-----------------------------------------------------------------------------

These are the things the ceremony exists to prove. They are all defensible
reasoning, and none of them has met a real server or the production database.

THE GMAIL LABEL-DROP MODEL. The code assumes that moving a message to
[Gmail]/Trash drops its other labels server-side, so undo issues a move back
FOLLOWED BY a set_labels restoring what from_state recorded. If Gmail turns
out to keep the labels, the restore is redundant but harmless; if it drops
more than assumed, the restore is what saves you. Three of the four mailboxes
here are Gmail, so this is the common path, not the edge case. Both
assumption sites carry comments naming what to correct:
server/mail/actions/kinds.ts:163 (the inverse sequence) and kinds.ts:223 (the
state model). Step 8 of the ceremony is where you find out.

recordFromState'S FIRST-WRITE-WINS WHERE CLAUSE. journal.ts:83 updates only
where from_state_json IS NULL or empty, so a retry can never overwrite the
pre-state a crash left behind. That statement cannot be executed in a test —
production is the only database this project has — so the ceremony is the
first time it ever runs.

createDatabaseJournal HAS NO TEST BEHIND IT, for the same reason: it is the
real-database implementation, and the tests all drive fakes. It now has live
callers in server/orpc/mail.ts.

THE ORPCError WIRE MAPPING. NOT_FOUND for an unknown mailbox (server/orpc/mail.ts:77)
and FORBIDDEN for a disabled one (:80) have never been exercised without a dev
server. Worth one deliberate glance: pick a disabled mailbox in
the apply panel and confirm you get the amber "disabled" wording rather than
a red generic failure.

UNDO REFUSES AFTER AN \Archive OR \Trash FOLDER RENAME. undo.ts resolves its
targets from the server's live SPECIAL-USE attributes, so if a folder was
renamed or re-flagged since the action, the rebuilt plan does not match the
recorded to_state and undo declines rather than moving mail out of a folder
it was never in. If undo refuses, this is the likely reason, and refusing is
the correct behaviour — not a bug to work around.

JOURNAL DATE FILTERS USE LOCAL-DAY BOUNDS. journal.tsx widens each filter
date to that day's local edges (T00:00:00 and T23:59:59.999). If the server's
timezone differs from the browser's, rows near midnight can appear on the
neighbouring day. Widen the range by a day before concluding a row is missing.


-----------------------------------------------------------------------------
WHAT PHASE 4 DELIBERATELY LEFT OUT
-----------------------------------------------------------------------------

file DECISIONS ARE NOT APPROVABLE. DO NOT TRY. §6's client axis is Phase 5,
so filing has no executor, and deferred is a TERMINAL state: promotion only
moves rows that are still shadow, and an apply run only reads pending, so a
row the executor defers can never be picked up again by anything in this
phase. There were roughly 2,366 file decisions across the backlog when this
was written; approving them would park all 2,366 somewhere Phase 5 could only
reach with hand-written DML. /admin/shadow refuses the approval in both
scopes for exactly that reason — a disabled button here is the feature. A row
already promoted before this gate existed still applies as deferred, and that
part is a designed outcome, not a failure.

purge DOES NOT EXIST. §1.7 keeps it for Phase 8, behind a separate scheduled
sweep. Trash is reversible; permanent deletion is not in this phase at all.

NOTHING MAY SET autonomy: "auto". §8 reserves promotion-to-auto for Phase 6.
Phase 4 is propose-only: every single mutation waits on a human click. There
is no code path that acts on its own.

RESCUE DETECTION IS PHASE 6. Until then, a policy that makes a mistake stays
active until YOU suspend it, and the Action Journal is the only mechanism
that will show you it happened. Read the journal after a batch, not just the
counters.


=============================================================================
PHASE 5 — FILING TO CLIENT FOLDERS (added 2026-08-20)
=============================================================================

Phase 5 makes the `file` action real. A `file`-classed message is now filed
into a folder derived from its sender policy's client/topic mapping, rendered
with the destination mailbox's own hierarchy delimiter, and created on first
use if it does not already exist. Anything that cannot be resolved or is not
trustworthy enough to file automatically lands in a `filing_queue` instead,
with a reason attached.

Nothing in Phase 5 has ever run against a real IMAP server. Every mutating
path — the resolver's createFolder call, the executor's file mutation, undo's
filing-aware resolution — was verified by typecheck, by unit tests over a fake
provider, and by reading. Those tests assert which calls get issued; they
cannot prove a real server folder list, delimiter, or CREATE response behaves
the way the code expects. So, exactly as Phase 4's ceremony was the real
acceptance test for the executor and undo, the sequence below — specifically
steps 5 through 7 — is the first time filing touches real mail. Do it once,
deliberately, on one message and one sender whose destination is obvious.


-----------------------------------------------------------------------------
THE ORDER — EACH STEP DEPENDS ON THE ONE BEFORE IT
-----------------------------------------------------------------------------

  1. Apply migrations 0005 and 0006:

         bun run db:migrate

     Both are pending as of this write-up; neither has been applied. 0005
     adds Action.mailboxId (see the Phase 4 section above — if you are doing
     Phase 4's and Phase 5's migrations in the same sitting, one db:migrate
     run applies both in order). 0006 (server/db/migrations/0006_confused_fenris.sql)
     adds the FilingBinding table — the operator's "this logical path already
     has a home" bindings — and Action.targetPath, the column filing writes
     its proposed destination into. Nothing below works until both exist.

  2. Dry run the mapping seed:

         bun --env-file=.env scripts/seed-filing-mapping.ts

     Read the output. Expect 41 senders mapped, 1 unmapped
     (contact-form@tellmann.co.za, deliberately — it is inbound leads from the
     operator's own site and the triage doc calls it "worth a look before
     filing", a destination the operator has not decided yet), and 8
     FilingBinding rows proposed for felix@tellmann.co.za, none for the three
     Gmail mailboxes (they have no user labels to preserve, so every logical
     path renders fresh there).

  3. Apply the seed:

         bun --env-file=.env scripts/seed-filing-mapping.ts --apply

     The script preflights that FilingBinding actually exists and refuses
     with a named error if step 1 has not happened — it will not commit a
     mapping half of the write with no binding half to match it. All of its
     writes (both the SenderPolicy updates and the FilingBinding inserts) run
     inside one transaction, so a failure partway through leaves the database
     exactly as it was.

  4. Run a FRESH shadow pass:

         bun --env-file=.env tmp/run-shadow.ts

     REQUIRED, not optional. Action.targetPath is written at decision time —
     the shadow runner computes and stores the proposed folder path the
     moment it journals a `file` decision, not later when the row is
     approved. Every Action row minted BEFORE step 3 landed the mapping was
     computed against a sender policy with no client/topic set, so it carries
     no proposal and resolves to `no_mapping` in the filing queue. Skipping
     this step means every visible `file` decision queues instead of files,
     for a reason that looks like a bug and is actually stale data.

  5. Review the shadow report at /admin/shadow and approve exactly ONE `file`
     decision, on a sender whose destination is obvious (one of the 41 mapped
     senders, ideally one bound to an existing tellmann folder rather than one
     that will mint a brand-new one on the first try).

  6. Apply it from /admin/mail. THIS CREATES A FOLDER ON A REAL SERVER if the
     resolved path is not already bound to an existing one. Check the folder
     appeared where expected: right name, right delimiter. On
     felix@tellmann.co.za that is `.` (so a `Clients/Listify` mapping with no
     binding renders as `INBOX.Clients.Listify`); on any of the three Gmail
     mailboxes it is `/`. If the sender is one of the 8 bound paths, confirm
     the message landed in the operator's existing folder rather than a new
     one beside it.

  7. Undo it. Check the message went back to where it started. Undo does NOT
     remove the folder step 6 created, and does not try to: it restores the
     message, and an empty folder it leaves behind is not a mutation worth
     reversing. Undo also never CREATES a folder, on purpose — it resolves
     the filing destination the same way the executor did, but only to find
     where the message should return to, never to manufacture a place for it
     that did not already exist.

  8. Only then look at /admin/filing, the queue. Every message the DKIM gate
     held back, every unmapped sender, and anything else that could not
     resolve lands here with a reason attached (`no_mapping`,
     `dkim_unaligned`, `ambiguous_client`, or `unresolvable_folder`). Approve
     a batch from here only after steps 5 through 7 have proven the single-
     message path works end to end.


-----------------------------------------------------------------------------
WHAT WAS MEASURED, AND WHAT WAS NOT
-----------------------------------------------------------------------------

MEASURED, against the live database, before any live IMAP mutation: the 41/1
mapping split above, the 8 FilingBinding rows for felix@tellmann.co.za, the
DKIM alignment rates by mailbox that motivated amending §6's gate to
address-scope-only (recorded in server/mail/filing/paths.ts), and that 40 of
the 41 seeded `file` policies are address-scoped so the amended gate applies
to nearly all of them.

NOT MEASURED, until an operator runs steps 5 through 7 above: whether
createFolder's CREATE actually lands where findNamespaceRoot's INBOX-rooted
detection predicts on felix@tellmann.co.za; whether a Gmail label created via
mailboxCreate behaves the way the resolver assumes (a top-level label, not
INBOX-rooted); whether a bound path's folder name — e.g. "INBOX.Finances -
Ref", with a space and a hyphen — round-trips through the IMAP LIST/CREATE
cycle without being mangled; and whether undo's filing-aware resolution
actually finds the message back in its origin folder rather than declining,
the same class of risk the Phase 4 section above documents for the archive
and trash paths. Every one of these is reasoned about in code comments in
server/mail/filing/resolver.ts, render.ts and paths.ts; none of them has met a
real server. The ceremony above is what proves or disproves that reasoning.
